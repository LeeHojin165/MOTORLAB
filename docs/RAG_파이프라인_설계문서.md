# RAG 파이프라인 설계문서 — MOTORLAB

전체 구조 그림: `docs/motorlab-architecture.png`

```
질문 ─▶ [수집] 프롬프트 1 검색어 추출 ─▶ 위키백과 검색 ─▶ 프롬프트 2 후보 선별 ─▶ 본문 수집 ─▶ 청킹 ─▶ car_docs 색인
                                                                                                     │
        ┌────────────────────────────── LangGraph ───────────────────────────────┐                   │
        │ retrieve: car_meta[차량 ID] (항상 [근거 1]) + car_docs(차량 ID 필터, 유사도/MMR) ◀─────────┘
        │           → 병합 · 중복 제거 · 번호 부여                                  │
        │ generate: 프롬프트 3 → [근거 n] 정규화 → 없는 번호 삭제 → 인용된 근거만 추출 │
        └────────────────────────────────────────────────────────────────────────┘
                                   ─▶ 화면: 답변 + 인용 근거(제목 · 출처 종류 · 원문 링크)
```

## 1. Vector DB 컬렉션 구조와 메타데이터

ChromaDB 1.5.9 · 거리 함수 cosine · 임베딩 `text-embedding-3-small`

| 컬렉션 | 단위 | 청크 ID | 메타데이터 필드 |
|---|---|---|---|
| `car_meta` | 차량 1대 = 청크 1개 (200개) | 차량 ID (예: `bmw-ix3-2026`) | `car_id`, `car_name`, `year`, `maker`, `fuel`, `drive_code`, `body_type`, `source_type="meta"`, `title`, `chunk_id` |
| `car_docs` | 외부 문서 청크 (현재 3,166개 · 문서 367건) | `{차량 ID}:{문서 ID}:{순번}` (예: `hyundai-pony-1975:ko-6a1209b6c7:3`) | `car_id`, `car_name`, `source_type`(wiki · pdf), `lang`(ko · en), `title`, `url`, `page`(PDF), `doc_id`, `query`(이 문서를 부른 검색어), `chunk_index`, `chunk_id`, `collected_at` |

**두 컬렉션으로 나눈 이유** — 선택한 차량의 제원은 질문과 유사도가 낮아도 항상 근거에 있어야 합니다. 메타데이터를 따로 두면 검색 없이 ID로 바로 꺼내 [근거 1]로 고정할 수 있고, 외부 문서만 의미 검색합니다. 조건 탐색(F2011)은 반대로 `car_meta` 전체를 검색합니다.

**`car_id`가 필수인 이유** — `car_docs` 검색은 `car_id` 필터로 범위를 좁힙니다. 이 필드가 없으면 다른 차량의 문서가 근거에 섞입니다. 청크 ID에도 차량 ID를 넣어, 여러 차량이 같은 문서(예: 「대량생산」)를 수집해도 서로 덮어쓰지 않게 했습니다.

**`doc_id`** — `{lang}-{md5(title)[:10]}`, PDF는 `pdf-…-p{쪽}`. 문서가 짧아져 청크 수가 줄면 남는 이전 청크를 지웁니다(`index_document`).

## 2. 항목 텍스트 설계 (F2001)

사용자는 이름·연도·제조사뿐 아니라 "후륜 수동 쿠페", "제로백 4초 전기차"처럼 제원 조건으로도 차를 찾습니다. 그래서 제원 속성을 **모두** 한 텍스트에 넣었고, 값이 없는 속성은 빼지 않고 "확인되지 않음"으로 적어 LLM이 빈칸을 추측하지 않게 했습니다.

```
차량: BMW iX3 (노이어 클라쎄) (BMW iX3 (NA5)) · 2026년 · 제조사 BMW · 독일
기준 트림: iX3 50 xDrive · 차종: 중형 SAV · 동력원: 전기
엔진/모터: 전·후 듀얼 모터 · 108.7 kWh (800V, 6세대 eDrive) · 변속기: 1단 감속기 · 구동방식: 사륜구동 (xDrive) (AWD)
최고출력: 345 kW (469 PS) · 최대토크: 645 N·m
0–100km/h: 4.9초 · 최고속도: 210 km/h · 공인 연비/주행거리: WLTP 1회 충전 최대 805 km
전장 4,782mm · 전폭 1,895mm · 전고 1,635mm · 휠베이스 2,897mm · 공차중량 확인되지 않음
서스펜션: 앞 더블 조인트 스프링 스트럿 / 뒤 5링크
```

## 3. 문서 수집 · 청킹 · 색인 흐름 (F2003 ~ F2005)

1. **차량 자체 문서는 항상 색인** — `cars_enriched.json`의 문서 묶음(EN 200 · KO 145)을 쓰고, 없으면 영문 위키에서 직접 가져옵니다. 선별·길이 규칙보다 우선합니다(`ensure_own_docs`).
2. **같은 질문인지 확인** — (차량, 정규화한 질문)이 캐시에 있으면 그때 뽑은 검색어를 그대로 씁니다. 프롬프트 1은 temperature 0에서도 같은 질문에 다른 검색어를 낼 수 있어, 검색어 캐시만으로는 재수집을 막지 못했습니다(아래 8절).
3. **프롬프트 1 — 검색어 추출** (`gpt-4o-mini`) → JSON 배열, 최대 3개.
4. **검색어 캐시 확인** — 이미 수집한 (차량, 검색어)는 건너뜁니다.
5. **후보 수집** — 새 검색어마다 한국어 위키백과 검색 상위 4건. 이미 색인된 제목과 중복은 뺍니다.
6. **프롬프트 2 — 후보 선별** — 본문을 받기 **전에** 제목과 요약 160자만 보여 최대 3건을 고릅니다. 버릴 문서의 본문을 받지 않아 외부 호출이 줄어듭니다.
7. **본문 수집** — 고른 문서만 본문(최대 12,000자, 「같이 보기 · 각주 · 외부 링크」 이후 제거)과 원문 URL을 받습니다.
8. **청킹 · 색인** — `RecursiveCharacterTextSplitter`, 구분자 우선순위 `"\n== "`(위키 섹션) → 문단 → 줄 → 문장 → 공백. PDF는 쪽 단위로 먼저 나눈 뒤 같은 방식으로 청킹해 근거에 「파일명 p.쪽」을 표시합니다.
9. **캐시 기록** — (차량, 질문) → 검색어, (차량, 검색어) → 선별·제외 문서 제목 (`data/collect_cache.json`).

외부 호출이 막힌 환경에서는 `OFFLINE_COLLECT=1`로 문서 묶음만 씁니다. 수집이 실패해도 이미 색인된 문서로 답을 이어 가고, 화면에 그 사실을 표시합니다.

## 4. 검색 결과의 병합과 중복 제거 (F2006 · F2014)

1. `car_meta`에서 선택 차량 청크를 ID로 꺼내 **[근거 1]로 고정**합니다(검색하지 않음).
2. 검색 질의 = `"{차량명} {영문명} {질문}"` — "어떤 역사를 가진 차야?"처럼 대상이 빠진 질문에서도 그 차량 문서가 잡히게 합니다.
3. `car_docs`를 `car_id` 필터로 검색해 **Top-k − 1**건을 가져옵니다.
   - 유사도: `similarity_search_with_score`, 화면에 `1 − 거리`를 유사도로 표시
   - MMR: 후보 `max(MMR_FETCH_K, k×3)`건 → λ=0.5로 다양성을 반영해 k−1건 선택
4. **중복 제거** — 청크 ID가 같거나, 공백을 뺀 본문의 MD5가 같은 청크는 하나만 남깁니다(같은 내용이 KO/EN·여러 검색어로 들어온 경우).
5. 남은 순서대로 [근거 2], [근거 3] … 번호를 붙입니다.

## 5. 프롬프트 세 개 (`backend/domain/prompts.py`)

| | 역할 | 모델 | 입력 | 출력 형식 | 핵심 규칙 |
|---|---|---|---|---|---|
| **프롬프트 1** 검색어 추출 | 자동차 전문 큐레이터 | gpt-4o-mini | 차량(이름·영문명·연도·제조사), 질문 | JSON 문자열 배열 (최대 3) | 차량 이름 반복 금지, 질문과 관련된 기술·인물·사건, 너무 넓은 개념("자동차", "엔진") 금지, 필요 없으면 `[]` |
| **프롬프트 2** 후보 선별 | 자동차 전문 큐레이터 | gpt-4o-mini | 차량, 질문, 후보 `[번호] 제목 — 요약` | JSON 정수 배열 (최대 3) | 동명이의(영화·지명 등)·무관 문서·넓은 일반 개념 제외, 없으면 `[]` |
| **프롬프트 3** 답변 생성 | 자동차 제원·역사 큐레이터 | gpt-4o (화면에서 gpt-4o-mini · Claude Sonnet 4.5 선택) | `[근거 n] (출처 종류) 제목 + 본문` 목록, 질문 | 본문 + `[근거 n]` 표기 | 근거만 사용, 없으면 "제공된 문서에서 확인되지 않습니다", 사실 문장마다 [근거 n], 기준 트림 명시, 근거끼리 값이 다르면 둘 다 제시, 지시문·원문 그대로 출력 금지 |

JSON 응답은 `parse_json`이 코드 블록·앞뒤 설명을 걷어 내고 첫 JSON 값을 꺼냅니다. 파싱에 실패하면 빈 배열로 처리해 수집만 건너뜁니다.

## 6. 청크 크기 · 중복 길이 · Top-k

| 설정 | 값 | 이유 | 바꿨을 때 (실측) |
|---|---|---|---|
| `CHUNK_SIZE` | 1,000자 | 위키 섹션 하나(예: 「생산」, 「엔진」)가 대체로 한두 청크에 들어가 제원·연혁 서술이 중간에 끊기지 않는 크기 | 포드 모델 T 문서 2건: 1000/200 → **11개**, 500/100 → **26개**. 500자에서는 표와 설명이 갈라져 한 근거에 수치와 맥락이 함께 오지 않음 |
| `CHUNK_OVERLAP` | 200자 | 청크 경계에 걸친 문장이 양쪽 어디서든 온전히 검색되도록 | 1000/400 → **12개** (중복을 늘리면 청크 수와 임베딩 비용이 늘고, 겹치는 청크가 근거에 몰림) |
| `TOP_K` | 6 (메타 1 + 문서 5) | 근거 프롬프트가 약 5,000~6,000자 안에 들어오고, 제원 질문(메타 위주)과 역사 질문(문서 위주) 모두 답할 수 있는 양 | 같은 질문 Top-k=3 → 근거 3건(KO 1 · EN 1 청크), Top-k=8 → 8건(EN 청크 5개 추가). 화면에서 2~15 사이로 조정 |
| `SEARCH_TYPE` | similarity (MMR 선택 가능) | 기본은 관련도 우선 | Top-k=6에서 근거 1~3은 같고 4~6이 다름: 유사도 = 청크 3·6·2(앞부분에 몰림), MMR = 청크 6·5·8(문서 뒷부분까지 퍼짐) |

청크 설정을 바꾸면 `python -m scripts.build_index --reset --bundle`로 다시 색인합니다. 실측 로그: `docs/evidence/05_chunk_setting.txt`, `06_09_16_20_rag.txt`.

## 7. 답변에 근거를 표시하는 방식 (F2008)

1. `[근거 1, 3]` → `[근거 1][근거 3]`으로 정규화합니다.
2. 근거 목록에 없는 번호(LLM이 지어낸 번호)는 본문에서 지웁니다.
3. 본문에 실제로 나온 번호의 근거만 「답변에 사용한 근거 n건」으로 표시합니다. 각 근거에는 번호 · **출처 종류 배지**(메타데이터 / 위키백과 KO / 위키백과 EN / PDF) · 제목 · 160자 발췌 · 청크 ID · 유사도(또는 「항상 포함」, 「MMR 선택」) · 원문 링크가 붙습니다.
4. 본문의 번호를 누르면 해당 근거로 이동합니다.
5. 인용된 근거가 0건이면 "답변에 인용된 근거가 없습니다. 색인된 문서에서 확인되지 않는 내용일 수 있습니다."를 표시합니다.
6. 설정에서 「검색됐지만 인용되지 않은 근거」도 따로 볼 수 있어, Top-k나 MMR을 바꿨을 때 차이를 확인할 수 있습니다.

## 8. 도메인 특화 기능 설계 이유 (F2010 · F2011)

- **제원 비교** — 자동차 질문에서 가장 흔한 것이 "A와 B 중 어느 쪽이 더 빠른가/큰가"입니다. 근거를 두 차량의 메타데이터 청크로 한정해, 시대가 다른 차를 비교할 때 LLM이 근거 없는 수치를 끼워 넣지 못하게 했습니다. 값이 없으면 "확인되지 않음"으로 둡니다.
- **사실 확인** — 커뮤니티에서 도는 "아우디 콰트로는 5기통 터보 사륜구동이다" 같은 주장을 문서로 판정합니다. MMR(Top-6)로 근거를 넓게 모으고, 사실 / 사실 아님 / 확인 불가 세 가지로만 답하게 해 "애매하면 확인 불가"로 떨어지게 했습니다.
- **조건 탐색** — `car_meta` 유사도 상위 20대를 후보로 가져온 뒤, LLM이 조건을 **모두** 만족하는 차량만 고르고(확인할 수 없는 조건이 있으면 제외), 후보 목록에 없는 car_id는 서버에서 버립니다. 정확도를 우선해, 조건에 맞지만 후보 20대 밖에 있는 차량이 빠질 수 있습니다.

## 9. 선택한 이유 · 겪은 문제 · 해결

| 문제 | 원인 | 해결 |
|---|---|---|
| **같은 질문을 다시 물었는데 문서가 또 수집됨** (셀프 점검 4번) | 캐시 키가 (차량, 검색어)뿐이었고, 프롬프트 1이 같은 질문에 다른 검색어를 냄(예: 2회차에 "아우디 스포츠카", "사륜구동 시스템") | (차량, 정규화한 질문) → 검색어 캐시를 추가해 같은 질문이면 프롬프트 1부터 건너뜀. 재검증: 2·3회차 0.0초, 청크 수 불변 (`evidence/04_collect_cache_fixed.txt`) |
| 색인 후 서버에서 "hnsw index 로드 실패" | ChromaDB 1.5.x가 한글 경로의 HNSW 파일을 다시 읽지 못함(청크 약 1,000개 이상에서 드러남) | 경로에 비ASCII가 있으면 DB를 `~/.motorlab/chroma`에 자동 배치 (`config._chroma_dir`) |
| 위키백과 요청이 50초씩 막힘 (HTTP 429) | 차량마다 4~6회 요청 | 데이터 준비 단계에서 최대 40대씩 묶어 요청, `Retry-After` 존중, 연락처 포함 User-Agent, 요청 간격 1초 |
| "어떤 역사를 가진 차야?"에 "확인되지 않습니다" | 질문에 차 이름이 없어 일반 문서("자동차")가 차량 문서를 밀어냄 | 검색 질의에 차량 이름을 붙이고, 프롬프트 1·2에 넓은 일반 개념 제외 규칙 추가 |
| 위키 대표 사진이 다른 세대의 차 | 모델 전체 문서는 최신 세대 사진을 씀 | 200장을 직접 검수해 세대에 맞는 Commons 파일을 지정, 제원은 인포박스와 자동 대조(`data/verify_report.md`) |
| 메타데이터와 위키 값이 다름 (예: 포니 80 PS vs 55 PS) | 트림·시장·측정 기준 차이 | 프롬프트 3에 "근거끼리 값이 다르면 둘 다 출처와 함께 제시" 규칙. 메타데이터에 기준 트림을 명시 |
